Kubernetes · Azure DevOps · SRE

AKS + Helm delivery with SRE guardrails

Source on GitHub ↗

Operational workflow

  1. CI: unit tests, helm lint and render, image build, Trivy scan that fails on CRITICAL, push to ACR tagged with the build.
  2. Staging: helm upgrade --install --atomic; a failed rollout rolls back automatically, then a smoke test.
  3. Production: environment approval check, then the same atomic upgrade.
  4. Operate: burn-rate alerts page on fast error-budget burn and link to an incident runbook; the budget policy freezes risky releases.

Problem

Releases to AKS with no safe rollback, no gate before production and no signal for whether users are affected.

Solution

A small API packaged as a Helm chart (non-root, liveness and readiness probes, HPA, PodDisruptionBudget), delivered by a multi-stage Azure Pipelines workflow, with a 99.5% / 28-day SLO and multi-window burn-rate alerts.

Technologies

  • Azure Pipelines
  • AKS
  • Helm
  • ACR
  • Docker
  • Trivy
  • Prometheus
  • Azure Monitor
  • OpenSLO

How it was verified

Unit tests, helm lint, helm template with production values, and a smoke test of the running app execute in GitHub Actions on every push. Not deployed to a real AKS cluster.

CI/CD · DevSecOps

GitHub Actions DevSecOps pipeline

Source on GitHub ↗

Operational workflow

  1. Lint (Ruff with bandit rules), tests with an 80% coverage gate, Bandit SAST, Gitleaks and pip-audit run in parallel.
  2. Container job: build, smoke test against /healthz, fail if running as root, Trivy fails on fixable CRITICAL CVEs, CycloneDX SBOM saved as an artifact.
  3. A manual run on main reaches the demo-staging environment behind an approval.

Problem

Vulnerable code, leaked secrets and unsafe container images can reach an environment when security checks are optional or run late.

Solution

Every pull request runs five gates in parallel; the container job only starts when all pass, and promotion needs an environment approval. Deployment to Azure is documented with OIDC federated credentials, so no secrets are stored.

Technologies

  • GitHub Actions
  • Ruff
  • Bandit
  • Gitleaks
  • pip-audit
  • Trivy
  • CycloneDX
  • Docker
  • OIDC

How it was verified

The workflow runs on GitHub-hosted runners for every change to the project; results are on the repository's Actions tab. 8 unit and HTTP tests pass. No registry push or real deployment.

Azure Infrastructure · Infrastructure as Code

Terraform hub-and-spoke network on Azure

Source on GitHub ↗

Operational workflow

  1. Inputs validated in variables.tf with safe defaults; standard tags defined once in locals.
  2. terraform fmt -check, init -backend=false and validate run in CI on every push.
  3. The paid firewall and VPN gateway are deliberately not created; DR and cost levers are documented with RTO/RPO targets.

Problem

Networks built by hand drift between environments, let workloads talk to each other freely and are hard to audit for tags, backup and cost.

Solution

A hub VNet with firewall, gateway and shared-services subnets; spokes that peer only with the hub; NSGs that default to deny; a private DNS zone; one tag set on every resource; a Recovery Services vault with a daily policy and an optional DR vault.

Technologies

  • Terraform
  • azurerm
  • VNet peering
  • NSG
  • Private DNS
  • Log Analytics
  • Azure Backup
  • Site Recovery

How it was verified

terraform fmt and terraform validate pass in GitHub Actions. plan and apply need an Azure subscription and are out of scope.

Observability · Incident response

SLO burn-rate alerting and incident flow

Source on GitHub ↗

Operational workflow

  1. The service exposes Prometheus metrics; errors and latency can be injected to rehearse incidents.
  2. Recording rules compute error ratios over 5m, 30m, 1h and 6h; alert rules are unit-tested with promtool.
  3. Pages link to runbooks for budget burn and latency; incidents end in a blameless RCA from a template.
  4. An offline calculator reports budget used and exits with code 2 on a page-level burn, so it can gate a release.

Problem

Alerts on raw error spikes page people for blips and still miss slow, steady budget burn.

Solution

An SLI (non-5xx share of requests) and a 99.5% / 30-day SLO with multi-window burn-rate alerts: page at 14.4x over 1h and 5m or 6x over 6h and 30m, ticket at 1x over 3 days. Alertmanager separates pages from tickets and suppresses noise when the target is down.

Technologies

  • Prometheus
  • Alertmanager
  • Grafana
  • promtool
  • Docker Compose
  • Python
  • SLI/SLO

How it was verified

11 Python tests pass; promtool check and test rules, amtool check-config and the Compose file are checked in GitHub Actions. On the synthetic data the calculator reports 47.4% of the budget used and a 34x page-level burn (synthetic numbers, not a real system).
